# 逻辑答疑系统 MVP

本项目是“逻辑答疑系统”的可运行 MVP。系统以确定性验证为中心：自然语言解析、OCR 和教学表达只负责输入与交互，命题推理、真值模型枚举和组合约束求解负责给出可复现的结论。

当前已支持结构化命题逻辑的前向推理、逆否推理、全局矛盾检测和证明轨迹；受控中文条件解析；“一定/可能/不可能/无法推出”四类选项验证；排序、分组和一对一匹配约束求解；图片 OCR 与逻辑关键词校正；用户结构化解法批改、错因标签与学习档案；以及题库审核、运行指标和本地发布门禁。

## 技术路线

技术栈为 Python 3.12+、FastAPI、SQLite 和自研的轻量逻辑/约束求解内核。所有最终结论都由规则引擎或完整枚举验证；当题干矛盾、求解无解或超过安全搜索上限时，接口会显式返回相应状态，而非生成未经验证的答案。

API 适配层按职责拆分：`api.py` 负责应用装配、通用求解、学习档案、OCR、中文解析和运行指标；`api_security.py` 集中维护受信代理身份及管理员鉴权依赖；`question_bank_api.py` 独立承载候选快照、审核、形式化资产转换和发布路由。题库存储通过依赖注入取得，保留测试环境替换独立 SQLite 存储的能力，公开接口路径和 DTO 不变。

当前交付路线已经完成：命题逻辑内核 → 受控中文条件解析 → 选项验证器 → 排序/分组/匹配求解器 → OCR 校正 → 结构化解法批改与学习档案 → 审核、指标和质量门禁。后续扩展应优先补充经审核题库、语义覆盖范围和远程 CI，而不绕过现有确定性验证链路。

### 分步实施计划

已完成第 1 步“可验证命题逻辑内核”：支持事实、单前提蕴含、前向推理、逆否推理、全局矛盾识别、可追溯证明步骤和结构化求解 API。矛盾检测覆盖整个知识库：即使冲突命题与查询无关，系统也会上报 `inconsistent` 并通过 `conflict` 字段指出冲突对，同时把验证等级降为 `inconsistent_conditions`。

第 2 步已完成受控中文条件解析，覆盖“如果/若/只要”“只有……才……”、明确的“当且仅当……”以及单个“不”否定等句式；解析出的事实和规则会在接口中回显。包含除非、析取、合取、量词或非标准否定的条件不会自动猜测，而是返回结构化人工确认请求；只有用户提交对应的事实或单前提规则转写后，才进入确定性逻辑内核。第 3 步已完成四类选择题的全模型验证与正反例构造。第 4 步已完成排序、分组与匹配题的结构化约束求解。第 5 步已完成 OCR 校正、结构化解法批改、错因标签和最小学习档案闭环。第 6 步已完成题库审核元数据、受认证身份保护的管理接口和本地发布门禁。

### 阶段 2.1：受控中文条件语法

中文自然语言存在大量歧义，因此解析器区分“可自动形式化”和“必须人工确认”两类条件。每个句子以句号、分号或换行分隔。自动路径只接受单层、单前提、单结论的明确句式，以及形式完整的“当且仅当 A，B”；解析器会保留原句作为规则的 `source_text`，接口在展示结论前回显解析结果。复杂条件不进入任何推理或模型枚举，直到用户给出结构化确认。

| 支持表达 | 示例 | 规范化结果 |
| --- | --- | --- |
| 事实 | `甲参加。` | `甲参加` |
| 否定事实 | `甲不参加。` | `¬甲参加` |
| 充分条件 | `如果甲参加，那么乙通过。` | `甲参加 → 乙通过` |
| 充分条件 | `若甲参加，则乙通过。` | `甲参加 → 乙通过` |
| 充分条件 | `只要甲参加，就乙通过。` | `甲参加 → 乙通过` |
| 必要条件 | `只有甲参加，乙才通过。` | `乙通过 → 甲参加` |
| 否定结论 | `如果甲参加，那么乙不通过。` | `甲参加 → ¬乙通过` |
| 双条件 | `当且仅当甲参加，乙通过。` | `甲参加 → 乙通过` 且 `乙通过 → 甲参加` |

文字必须是简单的“主体 + 状态”短语。否定仅支持主体和状态之间的单个 `不`，例如 `乙不通过` 被规范化为 `¬乙通过`。`除非/否则`、`至少/至多`、`或者/或`、`并且/且/同时`及 `不是/未/无/非` 不会自动转换；接口将返回 `confirmation_required=true`、原始句子、语义风险代码和说明，且验证等级明确为 `not_verified_pending_human_confirmation`。调用方必须在同一请求的 `confirmations` 中用事实和单前提规则完成逐句转写，例如将“除非甲参加，否则乙通过”人工确认成 `¬甲参加 → 乙通过`；未确认、重复确认或确认非待确认原句都会被拒绝。这样既保留了复杂题干的接入入口，也不会让系统自行假定其逻辑方向。

阶段 2.1 的验收样例包括：上述自动表达必须分别生成对应事实或规则；复杂表达必须稳定返回确认请求，而非返回证明或反证；确认后的结构化规则才可进入求解；`如果甲参加，乙通过`、`只有甲参加，乙通过`、空文本和不完整确认必须返回清晰错误。

### 阶段 3.1：命题逻辑模型枚举边界

选择题验证不能仅依赖已知事实的正向推导，还必须检查题干允许的全部真值模型。第一版模型枚举器仅处理当前已有的原子命题、事实和单前提蕴含规则；每个符号只能取真或假，模型必须同时满足所有事实与规则。规则 `P → Q` 只排除 `P` 为真且 `Q` 为假的赋值，其他赋值均为合法模型。

为了保证响应时延，首版最多枚举 12 个不同命题，即最多检查 4096 个候选模型。题干不存在合法模型时，枚举器返回 `unsatisfiable`，上层必须将其展示为条件矛盾；符号数量超过上限时，返回 `symbol_limit_exceeded`，上层不得把未枚举完成的结果标为已验证。模型需要以可读的正负命题清单输出，供后续“一定为真”“可能为真”等选项验证器构造正例和反例。

阶段 3.1 的验收标准是：枚举器能正确过滤违反事实或规则的赋值；能够发现无解的矛盾条件；能稳定输出真值模型；超过 12 个符号时安全拒绝枚举，不产生不完整结论。

### 阶段 3.2：选择题验证语义

选择题的每个选项在第一版中都是一个原子命题或其否定。验证器基于全部合法模型，而不是基于语言模型猜测，按以下规则判定：对“一定为真”，所有合法模型均满足该选项才通过；对“可能为真”，至少一个合法模型满足该选项才通过；对“不可能为真”，所有合法模型均不满足该选项才通过；对“无法推出”，至少存在一个合法模型不满足该选项才通过。

验证器会保留一个最小可读的正例或反例模型：可能为真和不可能为真失败时展示满足选项的正例；一定为真和无法推出时展示违反选项的反例。若模型枚举返回 `unsatisfiable` 或 `symbol_limit_exceeded`，选择题验证被阻断，并明确返回未验证原因，绝不以空模型集合得出“必然”或“不可能”的结论。

### 阶段 4.1：排序题约束模型与安全边界

排序题第一版使用显式对象列表和结构化约束，不直接猜测中文条件。支持三类两两关系：`before` 表示左侧对象排在右侧对象之前，`adjacent` 表示两者相邻，`not_adjacent` 表示两者不相邻；同时支持 `fixed_position` 指定某对象位于从 1 开始计数的位置。每个约束都必须引用对象列表中唯一存在的对象，固定位置必须落在有效范围内。

求解器通过枚举全部排列验证约束，并在不超过 8 个对象时给出完整解空间。因此返回的 `solution_count` 是精确值，`sample_solutions` 仅为便于阅读而截取的展示样本，不影响验证完整性。对象数超过 8 时，系统返回 `item_limit_exceeded`，不会进行部分搜索或给出不可靠的结论；若不存在满足全部条件的排列，则返回 `unsatisfiable`。

阶段 4.1 的验收标准是：正确筛选先后、相邻、不相邻与固定位置约束；拒绝未知对象、重复对象、无效位置和自关联约束；循环或冲突条件应在有限时间内返回无解；接口应明确区分完整求解、无解和超出安全上限。

### 阶段 4.2：分组与匹配约束模型

分组题第一版使用对象、分组名称和每组最大容量的结构化输入。所有对象都必须被分配到一个组；支持 `same_group` 和 `different_group` 两类两两约束。容量只表示上限，不自动要求每组恰好坐满。求解器枚举全部可行分配，并通过候选分配总数上限 100,000 控制复杂度；超过上限时返回 `search_limit_exceeded`，不会进行部分搜索。

匹配题第一版使用等长的对象列表和目标列表，保证每个对象恰好匹配一个目标且每个目标恰好使用一次。支持 `fixed_match` 与 `forbidden_match` 约束。匹配求解同样采用全排列枚举，最多支持 8 个对象或目标；输入规模更大时明确拒绝。两个求解器都返回精确解数与少量展示样例，确保“可能/唯一/无解”等后续判断能够建立在完整解空间上。

阶段 4.2 的验收标准是：分组器正确处理容量、同组和异组条件；匹配器正确处理固定与禁止配对；两者均拒绝重复或未知对象、非法容量、错误的匹配规模；冲突条件返回无解，超出搜索边界返回未验证状态。

### 阶段 5.1：图片 OCR 与用户校正边界

图片接入不直接调用题目求解器。系统先接受 Base64 编码的 PNG、JPEG 或 WebP 图片，限制解码后大小不超过 10MB，并交给经过审核的 OCR Provider。当前 MVP 提供本地 Tesseract 适配器；如果部署环境没有安装该引擎，接口明确返回“OCR 不可用”，不会编造识别文本。Provider 是可替换接口，后续可接入经过安全审核的企业 OCR 服务。

识别结果必须原样返回，并标记题干中的高风险逻辑词，例如“如果、只有、只要、除非、至少、至多、不是、不、才”。用户在提交给中文解析器前可以通过校正接口修改文本；一旦校正前后高风险词的出现次数变化，系统会返回 `requires_confirmation=true` 并要求用户再次确认。OCR 结果和校正文案默认只在本次请求中处理，不在此阶段持久化保存。

阶段 5.1 的验收标准是：拒绝空、超限或非图片数据；本地 OCR 缺失时可解释地降级；识别后的高风险词能被标记；校正后的文本不能为空，且对关键逻辑词的修改必须被提示；所有 OCR 文本必须由用户确认或校正后，才允许进入后续解题流程。

### 阶段 5.2：用户解法批改与错因诊断边界

第一版仅批改结构化的单前提推理步骤，而不将自由文本“猜测”为证明。每一步需要提交引用的原始规则编号、前提、结论和推理方向：`forward` 表示按原规则推导，`contrapositive` 表示按逆否规则推导。批改器逐步检查规则编号、方向、前提是否已由题干或前序正确步骤建立，以及结论是否与所选规则一致；一旦发现问题即定位首个错误步骤。

当前能够诊断的错因包括：`invalid_converse`（误用逆命题或反向推导）、`wrong_rule_application`（规则方向或结论不匹配）、`premise_not_established`（前提尚未成立）、`invalid_rule_reference`（引用了不存在的规则）和 `missing_key_step`（步骤本身正确但尚未推出目标结论）。每个错因都会关联最小知识点标签，例如“逆命题与逆否命题”“前提核验”“条件推理”。如果题干本身矛盾，批改器直接阻断，不评价用户推理正确性。

阶段 5.2 的验收标准是：正确步骤能按顺序通过；误用逆命题能定位到首错并给出规则方向说明；未建立前提、无效规则引用和漏步骤能清晰区分；批改结论必须引用同一确定性逻辑内核的基准验证结果，不能由语言模型单独裁决。

### 阶段 5.3：学习档案、练习方向与隐私边界

学习档案第一版只保存经认证用户主动提交的最小学习记录：服务端身份主体、题目标识、题型、对错、错因标签、知识点标签和作答时长。服务端生成记录编号与 UTC 创建时间；不保存题干原文、图片、OCR 结果、自由文本解法或模型内部提示。所有数据库读写均使用参数化 SQLite 语句，学习档案接口从受信身份提供方取得主体，不接受客户端提交的 `user_id`，也不提供跨用户查询或全量导出接口。

学习画像按当前认证主体范围聚合总练习量、正确率、错因频次和知识点掌握度。推荐不伪造题目，而是基于最高频错因和低正确率知识点给出“练习方向”和最小练习建议；真正的同类题推荐需要在题库阶段接入经审核的题目资源。用户可删除单条记录，删除操作以认证主体和记录编号共同约束，避免跨用户误删。

阶段 5.3 的验收标准是：新增记录、按用户获取画像与删除单条记录均可用；不同用户的数据严格隔离；删除后画像即时反映结果；推荐仅依据用户自身标签和统计生成；数据库路径可通过部署配置覆盖，默认数据文件位于项目内的 `data/` 目录。

### 阶段 6.1：题库审核、运行指标与发布门禁

题目进入正式题库前必须经过审核。审核记录保存题目标识、审核人标识、审核状态、已核验答案、形式化版本和必要备注；每次更新会同时保留一条追加式审计事件。只有 `approved` 状态允许进入后续正式题库接入，而且通过审核必须同时提供已核验答案和形式化版本。当前 MVP 不保存题干正文，因此审核模块只管理题目元数据和审核结论。

运行指标只聚合路由模板、HTTP 状态码、请求数量和时延，不记录请求体、题干、用户标识、图片或 OCR 内容。学习档案与管理接口均要求由受信身份提供方验证身份。当前部署适配器假定前置可信代理在完成上游认证后注入 `X-Logic-QA-Subject` 和可选的 `X-Logic-QA-Roles`，并使用 `X-Logic-QA-Proxy-Token` 与环境变量 `LOGIC_QA_TRUSTED_PROXY_TOKEN` 进行通道校验；服务仅信任该代理，不接收客户端指定的 `user_id`、`reviewer_id` 或 `publisher_id`。管理接口额外要求角色 `logic_qa_admin`。未配置受信代理密钥时相关接口返回 503 并保持关闭。审核数据库路径可通过 `LOGIC_QA_REVIEW_DATABASE_PATH` 覆盖。

发布门禁要求：Ruff 静态检查、完整 pytest 回归测试和 Python 编译检查必须全部通过；任何新增题型、解析规则或求解器都必须补充成功、无解、边界超限和非法输入用例；正式题库中的每道 `approved` 题都应有对应的形式化版本与可复现的验证结果。仓库已提供 GitHub Actions 工作流 `.github/workflows/quality-gate.yml`：它会在推送到 `main` 与所有拉取请求中锁定依赖、执行 Ruff、全量 pytest 和编译检查。合并前应将 `Quality Gate / Verify Python 3.14` 设为受保护分支的必需状态检查。

### 阶段 7.1：内容绑定审核、版本化题库与真实练习推荐

题库发布采用“先提交内容摘要、审核精确绑定、再发布同一内容”的约束。管理员先提交完整候选内容，包括题目标识、内容版本、题型、题干、可选选项、错因标签、知识点标签、形式化版本，以及结构化形式化资产；系统以规范化后的全部内容计算 SHA-256 摘要。形式化资产通过 `kind` 明确绑定求解器：`propositional` 包含事实、单前提蕴含规则、查询、预期验证状态和预期答案；`ordering` 包含对象、先后/相邻/固定位置约束、预期求解状态和精确解数；`grouping` 包含对象、组别、容量、同组/不同组约束、预期状态和精确解数；`matching` 包含对象、目标、固定/禁止匹配约束、预期状态和精确解数。审核记录必须同时绑定 `question_id`、`content_version`、`content_hash` 和 `formalization_version`。只有审核状态为 `approved` 且四项绑定信息完全匹配的内容可以发布；题干、选项、标签、形式化版本或任何形式化资产改变，都会产生新的内容摘要并要求重新审核。

所有 SQLite 存储均通过版本化迁移表 `schema_migrations` 初始化，迁移在立即事务中执行，重复启动不会重放已记录版本；历史审核或题库表若缺少当前内容绑定字段，会被保留为带 `legacy_unbound` 后缀的归档表，不能混入新发布链路。每个存储均可创建一致性备份：系统通过 SQLite 原生 `backup()` 复制、`PRAGMA integrity_check` 校验、SHA-256 摘要和相邻 JSON 清单记录来源绝对路径及架构版本。恢复时必须从当前存储所属的清单加载，且来源路径、架构版本、摘要和 SQLite 完整性均一致，之后才使用临时库和原子替换覆盖目标。备份或清单遭篡改、来源库不匹配，或架构版本不兼容时，恢复操作会拒绝执行。

发布前，系统会按照资产类型重新调用确定性推理内核或完整枚举求解器。命题题的预期状态必须与复算状态一致，且结果不能是 `unknown` 或 `inconsistent`；组合约束题还必须使预期解数与完整枚举结果一致，且不允许无解或超过搜索上限。审核已核验答案必须与形式化资产中的预期答案一致。成功发布会保存一次追加式形式化验证事件，其中包含资产类型、预期和实际状态、预期和实际解数、命题证明步骤/冲突或组合题样例解，确保管理员可以回查当时的可复现依据。

选择题还必须在形式化资产中提交与展示选项等长、同顺序的 `option_assertions`。每条断言绑定一个选项，并声明该选项所对应的可复算状态；排序、分组和匹配题还必须声明该选项对应的精确解数。发布时系统将实际状态及实际解数与全部断言逐条比对，必须且只能命中一个选项，且该选项必须与 `expected_answer` 及审核的 `verified_answer` 一致。断言属于内容摘要的一部分，任何改动都会触发重新审核；审计事件会保存唯一命中的 `selected_option` 和完整的 `matching_options`，以便复核门禁行为。学习者响应不会暴露断言、预期答案或审核信息。

每个题目版本作为独立不可变记录保存；重新发布同一题目的新版本会在同一题库事务内将唯一旧活动版本标为非活动，并为该旧版本追加 `superseded` 生命周期事件。事件记录旧版摘要、发布人的受信身份、替代它的新版本、固定的替换原因和时间，因此自动替换也不会成为无审计的状态变更；若同题意外存在多个活动版本，发布会拒绝而非猜测替代关系。完整的发布、审核、形式化验证及生命周期审计事件均保留。管理员查询可查看内部元数据和形式化资产，学习者推荐只返回题干、选项、题型和匹配原因，不返回审核人、审核备注、答案、内容摘要、形式化版本、形式化资产、内部标签或其他用户数据。

用户练习推荐只从活动且精确审核通过的版本中选择。它会读取该用户自己的错因标签、知识点掌握度和已完成的发布题目版本，优先推荐匹配高频错因或低掌握度知识点的未尝试题目；没有个人历史时按稳定顺序返回基础题库候选。题库数据路径可通过 `LOGIC_QA_QUESTION_DATABASE_PATH` 覆盖。

阶段 7.1 的验收标准是：未审核、审核未通过、内容版本不一致、内容摘要不一致、形式化版本不一致、审核答案与形式化预期答案不一致、选择题缺少选项断言、断言与选项顺序不一致、断言零命中或多重命中、唯一命中选项与预期答案不一致、形式化结果不可复现、无法确定、存在矛盾、约束无解、搜索超限或声明解数与完整枚举不一致的题目均不可发布；新版本发布会保留旧版本历史但只激活最新版本；推荐结果只来自活动题目且不会重复当前用户已完成的同一版本；学习者 DTO 不含内部审核信息或形式化资产；推荐排序可由用户自己的错因与知识点统计解释；候选内容提交、审核和发布接口均必须由具备管理角色的认证主体访问。

### 阶段 7.2：认证学习者练习入口

同源页面 `/practice` 只供已经通过受信代理认证的学习者使用。它先读取当前用户的未尝试推荐，再以题目标识和内容版本读取活动发布版本的最小题目视图；题干与选项之外的内容摘要、审核信息、形式化资产、内部标签和正确答案均不出现在页面或学习者 API 响应中。浏览器提交的请求只包含所选选项和可选作答时长，不接受 `user_id`、正确性、错因或知识点标签。

服务端将作答与发布时的形式化验证审计事件精确关联，并以其中唯一的 `selected_option` 判分。正确性与学习标签由服务端写入当前认证主体的学习档案，响应只返回题目标识、版本、用户所选选项、对错和记录编号。已经作答的题目不会再次向同一用户推荐，也不能重复提交；不同认证用户的练习记录相互隔离。练习页刷新推荐列表时会保留已返回的判分反馈，确保用户能明确看到服务端结果后再选择下一题。

### 阶段 7.3：个人学习概览与受控复盘

同源页面 `/progress` 只读取当前认证学习者的已完成练习数、正确次数、正确率和服务端提炼的复盘方向。复盘 API 不会透出内部错因标签、知识点标签、标签计数、原始题目答案、审核信息或形式化资产；即使后端出现未知内部标签，也会归并为通用的“推理步骤复盘”，不将标签原文返回浏览器。已知的错因仅会映射为学习者可理解的抽象方向，例如“条件方向核验”或“前提核验”。

学习者记录确认也不再返回标签。服务端仍可在受控存储中使用标签计算个人推荐和复盘方向，但页面只能读取与当前认证主体绑定的聚合摘要；无身份或身份无效时，学习概览接口保持关闭。

### 阶段 7.4：内容版本感知的练习尝试账本

学习档案的练习记录现在精确绑定 `question_id + content_version`。历史通用学习记录保留为空版本，不会参与发布题练习的去重；正式练习提交必须携带发布版本。SQLite 迁移会为既有学习记录增加可空的内容版本字段，并对非空版本建立 `(user_id, question_id, content_version)` 部分唯一索引，因此同一认证用户对同一不可变发布版本只能成功记录一次，而不同用户可独立练习。

练习提交使用单条原子 `INSERT OR IGNORE` 作为唯一判定来源，不再依赖“先读取、再写入”的并发不安全流程。重复提交会得到 `409`，不会覆盖首次作答结果。推荐仅排除当前用户已经完成的精确版本：同一题目的旧版本完成后，管理员发布并激活新内容版本时，新版会重新进入该用户的候选范围。迁移回归、同版本并发提交、用户隔离和新版重新推荐均有自动化测试覆盖。

### 阶段 7.5：练习账本不可变性

已审核发布题的作答记录既是版本去重依据，也是学习概览的审计来源，因此学习者不能通过通用删除接口删除它们。通用学习记录仍可由所属用户删除；删除请求命中已绑定 `content_version` 的练习账本记录时返回 `409`，记录、版本去重状态和首次作答结果均保持不变。该限制同时避免了用户通过“删除后重做”覆盖服务端判分或重新打开同一发布版本推荐的路径。

### 阶段 7.6：受控练习记录更正申请

练习账本保持不可变，但学习者可以为属于自己的已发布题练习记录提交一次最小复核申请。申请仅包含记录编号和理由，服务端从认证主体和既有账本中绑定用户、题目标识和内容版本；客户端不能提交或覆盖原始对错、正确答案、内部标签、形式化资产或其他用户标识。通用学习记录不能进入该流程，跨用户记录按不存在处理。SQLite 通过 `record_id` 唯一约束与原子 `INSERT OR IGNORE` 防止同一练习记录在并发或重复请求下产生多条申请。

管理员使用独立的管理端接口读取并终态处置申请。当前状态保存在 `practice_correction_requests`，创建与处置同时写入 `practice_correction_events` 追加式审计表；已经处置的申请不能再次覆盖。处置结果仅表示“原记录已确认”或“需要按题库发布流程复核”，不会直接修改 `learning_records` 中的首次服务端判分、版本去重键、学习概览基础或推荐排除状态。学习者只能读取自身申请的最小状态，不会得到管理员身份、处置备注、题库答案或内部形式化信息。

### 阶段 7.7：更正处置衍生学习视图

学习者可通过 `GET /v1/learning/practice-correction-outcomes` 读取仅由自身申请当前状态派生出的安全结果视图。`pending` 只提示处理中，`record_confirmed` 只确认既有记录，`republication_required` 只说明题目将进入发布流程复核；该视图不返回申请理由、管理员身份、处置备注、正确答案、标签或形式化资产，也不会新增可修改的业务状态。

`republication_required` 不会自动改变原练习记录，更不会重新开放旧版本作答。只有管理员按照既有候选、审核、确定性形式化验证和发布门禁真正发布新的 `content_version` 后，版本化推荐才会把该新版本作为独立题目推荐给此前完成旧版本练习的学习者。由此，用户可获得明确状态说明，同时首次服务端判分、旧版本唯一作答约束与学习概览审计基础始终保持不变。

### 阶段 7.8：题库复核发布关联

管理员可在新版本已完成既有候选、审核、确定性形式化验证和发布门禁，且仍为当前活动版本后，通过 `POST /v1/admin/questions/{question_id}/{content_version}/correction-republication-links` 把一条 `republication_required` 申请显式关联到该版本。请求只接受申请编号与原内容版本；新版本号、内容摘要和关联人均由服务端从 URL、已发布题库记录和认证管理员身份取得，客户端不能夹带或覆盖这些审计字段。

关联记录存放于学习库的 `practice_correction_republications`，以申请编号为主键，并约束同一题目的新版本只能关联一条申请。成功关联会追加 `republication_linked` 事件，但绝不改写 `learning_records`、历史首次判分、旧版本唯一作答约束或发布状态。关联不是发布操作；新版本尚未发布、已非活动、题号或原版本不匹配、申请并非 `republication_required`，或者重复关联时，服务均会拒绝请求。

关联完成后，学习者的安全结果视图会显示 `republished_content_version` 和“复核后的新版本已发布”的说明，但仍不包含新版本内容摘要、管理员身份、审核备注、题目答案或形式化资产。读取该视图时，服务会再次核对关联记录中的版本和内容摘要是否仍可在题库中精确找到；若题库被独立恢复到不含该版本的快照，视图会安全降级为“将按发布流程复核”，不会把悬挂关联表述成已发布。新版本是否进入练习继续完全由既有版本化推荐判定；它不解除旧版本的限制，也不将处理申请本身等同于发布。题库和学习库使用独立 SQLite 文件，发布与关联按“先发布、后关联”顺序执行；若关联写入失败，新版本保持已发布，管理员可在修复原因后安全重试关联。

### 阶段 7.9：复核发布关联管理员审计查询

管理员可通过 `GET /v1/admin/practice-correction-audits` 分页读取只读审计视图，并按 `request_id`、`question_id`、原 `content_version`、`new_content_version` 和 `linked` 状态精确筛选；`GET /v1/admin/practice-correction-audits/{request_id}` 用于回查单条申请。每条审计视图统一包含当前申请、可选的不可变重发布关联，以及按追加顺序排列的 `requested`、`resolved`、`republication_linked` 事件链。它只读取既有学习库账本，不修改申请状态、练习记录、题库发布状态或学习者推荐。

该接口仅限具备管理角色的受信身份调用，因此管理员可追溯申请理由、处置人、处置备注、关联人、关联版本与内容摘要；学习者接口继续维持最小安全投影，不能访问该审计视图或其中的治理字段。查询标识为空、分页数量超出 1 至 100 的范围，或单条申请不存在时都会明确拒绝，不会放宽筛选条件或回退到其他记录。

### 阶段 7.10：受控版本下线与回滚治理

管理员可通过 `POST /v1/admin/questions/{question_id}/{content_version}/deactivation` 下线当前活动版本，并必须提交明确的治理理由。下线从活动状态读取、状态切换到 `deactivated` 审计事件追加均在同一立即写事务内完成；因此竞争下线同一版本时最多只有一个请求能提交事件，其余请求会明确得知版本已不再活动。下线只将该版本从学习者读取、推荐和判分路径中移除；题目的历史发布记录、候选快照、审核记录、形式化验证事件、学习账本及既有复核关联均不删除、不覆盖。题目可以暂时处于没有活动版本的状态，此时学习者无法读取或提交该题，但历史练习的首次判分和版本去重约束仍然有效。

历史版本可通过 `POST /v1/admin/questions/{question_id}/{content_version}/reactivation` 受控重新激活。该操作不创建新 `content_version`，不改写原始 `published_at`，也不伪装成新的发布；在切换活动版本前，服务会精确回读该历史发布版本的不可变候选快照和当前审核记录，要求审核仍为精确绑定的 `approved`，重新运行确定性形式化验证和全部选项语义门禁，并为本次复验追加新的验证事件。若同题存在另一活动版本，重新激活会在同一立即写事务内原子地下线它，并同时为被替换版本追加 `superseded` 事件、为重新激活版本追加 `reactivated` 事件；两条事实相互指向、共享操作者和时间，避免受控回滚留下单向审计链。若审核已撤销、候选快照缺失或复验失败，操作明确拒绝，原活动版本保持不变。

题库迁移 v2 新增追加式 `question_version_lifecycle_events`，审计记录包含动作、题目与版本、内容摘要、受信操作者身份、被替代或替代它的新版本、理由和时间；迁移 v3 以同字段重建和逐行复制扩展动作约束，保留已有事件及其追加顺序，并允许新版本发布时写入 `superseded`。迁移 v4 在 `question_versions(question_id)` 上增加仅对 `is_active = 1` 生效的部分唯一索引，从存储边界强制同一题目至多一个活动版本；升级发现既有库存在多个活动版本时会原子拒绝迁移，不会擅自选择或下线任一版本。迁移 v5 为生命周期审计表增加拒绝 `UPDATE` 与 `DELETE` 的 SQLite 触发器，阻止直接 SQL 绕过领域服务篡改或清除既有治理事件；升级仅新增保护触发器，不改写任何历史审计记录。迁移 v6 在写入前核验生命周期事件所指版本和内容摘要确实存在，并要求可选的替代版本属于同一题目；若升级发现历史事件引用缺失或摘要不一致的版本，会原子拒绝迁移，不会保留或修补不可信审计。迁移 v7 为 `question_formalization_verification_events` 增加同等的拒绝 `UPDATE` 与 `DELETE` 触发器，确保发布及受控重新激活时生成的可复现验证依据只能追加、不可被直接 SQL 改写或清除；升级仅添加保护，不改写既有验证审计。迁移 v8 在写入前核验验证事件所指版本和内容摘要确实存在于 `question_versions`；若升级发现历史验证事件引用缺失或摘要不一致的版本，会原子拒绝迁移，不会保留或修补不可信判分依据。迁移 v9 为 `question_candidates` 与 `question_publication_events` 增加同等的拒绝 `UPDATE` 与 `DELETE` 触发器：候选快照是发布与受控重新激活复验的回读事实，发布事件是发布者身份与时间的审计依据，两者从存储边界只能追加、不可被直接 SQL 改写或清除；升级仅添加保护，不改写既有快照与事件。发布、下线与重新激活均在获得立即写锁、完成当前活动状态完整性检查后才生成本次提交的统一时间，因此审计排序反映 SQLite 实际串行提交顺序而非请求抵达顺序。动作包括管理员显式触发的 `deactivated`、`reactivated`，以及新版本发布时自动写入旧版本的 `superseded`。管理员可通过 `GET /v1/admin/questions/{question_id}/version-lifecycle-events` 回查完整事件链；学习者不能访问该端点，也不会看到治理理由、内容摘要或管理员身份。该能力与更正申请重发布关联保持兼容：重新激活的历史版本不会被当作新的重发布版本，且已关联的新版本若不再活动，既有学习者投影会继续按题库的精确发布事实安全降级。

### 阶段 7.11：跨库重发布关联状态核验

管理员审计接口在保存学习库中不可变的重发布关联事实外，还会为每条已关联申请返回只读的 `republication_verification`。服务先核对关联题号与原内容版本是否仍和申请一致，再按关联的新版本及其内容摘要读取题库当前事实；整个过程不写入学习库、题库、审核库、生命周期事件或学习账本，也不会尝试修复发现的异常。

核验状态为 `active_verified` 时，关联版本仍存在、摘要精确匹配且当前活动；`historical_inactive` 表示版本和摘要仍存在但已被下线或替换；`missing` 表示题库当前不存在该版本；`content_hash_mismatch` 表示同版本的当前题库摘要与不可变关联摘要不一致；`request_binding_mismatch` 表示关联与申请的题号或原版本不一致；`unverifiable` 表示独立题库暂时无法可靠读取。除 `missing`、关联绑定异常和首次读取失败外，响应会回显题库实际观察到的摘要，供管理员审计比对。未关联申请的该字段为 `null`。学习者不能访问管理员审计接口，且既有学习者结果仍只在关联版本精确匹配且活动时显示“已发布”；若学习者读取期间题库暂时不可用或校验输入非法，结果会安全降级为“将按发布流程复核”，而非暴露底层错误或继续声称新版本可练习。

### 阶段 7.12：跨库重发布关联一致性巡检

管理员可通过 `GET /v1/admin/practice-correction-reconciliations` 分页巡检所有已存在不可变重发布关联。接口只接受管理角色的受信身份：`limit` 默认为 50、范围为 1 至 100，`offset` 默认为 0、范围为 0 至 10000；首次请求不传 `scan_boundary`，响应会返回一个持久、单调的扫描边界。后续页面必须回传该边界及 `next_offset`，以完成同一轮扫描。响应包含本轮冻结关联总数、请求偏移量、当前页扫描数、当前页 `active_verified` 数量和可继续读取的 `next_offset`；仅当还有未扫描的关联时才会返回下一个偏移量。

巡检会在同一学习库读取快照内同时取得扫描边界、关联总数、当前页申请、关联事实和事件链，避免统计与页面内容跨不同读取视图而出现自相矛盾。扫描期间新建立的不可变关联会获得更高的持久扫描序号，不会混入已开始的分页；它们会在下一次未指定边界的新巡检中被纳入。对每条关联，题库会在一次精确读取中同时返回历史发布事实与活动状态，避免版本存在性、内容摘要和活动状态跨不同题库读取视图而被误判。每页的 `non_verified_audits` 只收录当前核验并非 `active_verified` 的完整管理员审计视图，因此可直接定位下线、缺失、摘要错配、绑定错配或题库不可读等情形。学习库暂时不可读时接口返回 503，不返回可能不一致的部分计数或异常清单；题库暂时不可读时对应关联标记为 `unverifiable`。巡检复用既有只读核验，不写入或修复学习库、题库、审核库、版本生命周期事件和学习账本；它报告当前事实，不改写不可变历史关联，也不把异常自动解释为可发布状态。

## 快速启动

```powershell
cd E:\小玩意儿\logic-qa-system
uv sync --dev
uv run uvicorn logic_qa.api:app --app-dir src --reload
```

启动后访问 `http://127.0.0.1:8000/` 使用同源中文自主验证页，或访问 `http://127.0.0.1:8000/docs` 查看交互式接口文档。自主验证页会回显已解析事实、规则、验证等级和证明轨迹；遇到复杂语义时，只会收集用户明确填写的结构化确认并重新提交给后端，不会在浏览器端推断逻辑结论，也不会调用管理端接口。

访问 `http://127.0.0.1:8000/practice` 可进入已发布题目的练习页。该页面要求前置受信代理已配置 `LOGIC_QA_TRUSTED_PROXY_TOKEN`，并向服务注入代理令牌、认证主体和角色请求头；未认证时，推荐、读取题目和提交作答接口均会拒绝访问。练习判分始终由服务端使用发布验证审计记录完成，浏览器不会取得正确答案或审核、形式化资产。

访问 `http://127.0.0.1:8000/progress` 可查看当前认证学习者的练习概览和受控复盘方向。该页只展示聚合表现和安全映射后的建议，不返回内部标签、标签计数、题目答案、审核信息或形式化资产。

## 主要接口与部署配置

主要接口包括：`POST /v1/questions/solve` 用于结构化命题推理，`POST /v1/questions/solve-chinese` 用于中文条件解析、确认请求和确认后求解，`POST /v1/questions/verify-choice` 用于选择题选项验证，`POST /v1/questions/solve-ordering`、`solve-grouping` 和 `solve-matching` 用于组合约束题，`POST /v1/questions/ocr` 与 `/ocr/correct` 用于图片文字校正，`POST /v1/questions/review-solution` 用于结构化步骤批改，以及 `/v1/learning/*` 用于用户最小学习档案。`POST /v1/learning/practice-correction-requests` 允许学习者为自己的不可变发布题练习记录提交一次复核，`GET` 同一路径仅返回其最小申请状态；`GET /v1/learning/practice-correction-outcomes` 返回不含内部信息的派生处置说明。管理员可通过 `GET /v1/admin/practice-correction-requests` 查看申请，并以 `POST /v1/admin/practice-correction-requests/{request_id}/resolution` 追加终态处置；只有新版本已发布且活动时，才可通过 `POST /v1/admin/questions/{question_id}/{content_version}/correction-republication-links` 将 `republication_required` 申请显式关联到该版本。`GET /v1/admin/practice-correction-audits` 及其单申请路径提供仅管理员可见的关联、当前跨库核验状态和事件链审计查询；`GET /v1/admin/practice-correction-reconciliations` 以 `limit` 和 `offset` 分页巡检全部已关联申请，并仅返回当前非 `active_verified` 的完整审计项。管理端的 `POST /v1/admin/question-candidates` 需提交完整形式化资产，`GET /v1/admin/question-candidates/{question_id}/{content_version}/{content_hash}` 可精确回查候选快照，`POST /v1/admin/questions` 会在发布前复算并记录形式化验证依据。已发布活动版本可使用 `POST /v1/admin/questions/{question_id}/{content_version}/deactivation` 受控下线；历史已发布版本可使用对应的 `/reactivation` 在当前精确审核及确定性复验仍通过后重新激活；`GET /v1/admin/questions/{question_id}/version-lifecycle-events` 仅供管理员回查不可变的版本治理事件。

部署可通过 `LOGIC_QA_DATABASE_PATH`、`LOGIC_QA_REVIEW_DATABASE_PATH` 和 `LOGIC_QA_QUESTION_DATABASE_PATH` 指定 SQLite 文件路径。认证接口必须配置 `LOGIC_QA_TRUSTED_PROXY_TOKEN`；前置可信代理完成上游登录后，向服务注入 `X-Logic-QA-Proxy-Token`、`X-Logic-QA-Subject` 与 `X-Logic-QA-Roles`。学习者接口不再接收路径、查询参数或请求体中的用户标识，审核人与发布人也由认证主体自动写入。未配置代理密钥时身份相关接口默认关闭。OCR 默认依赖本地 Tesseract，未安装时会返回 503 和明确说明，不会伪造识别结果。
